# 04. Android 固有の技術制約と対応方針

| 項目 | 内容 |
|---|---|
| ステータス | ドラフト |
| 最終更新 | 2026-09-03 |

> **このドキュメントの位置づけ**
> アラームアプリは「機能」より「**確実に鳴ること**」が難しい。
> Android は省電力のためにバックグラウンド処理を積極的に殺すため、
> ここに書かれた項目を潰さないと「たまに鳴らないアラーム」が完成する。
> 各項目は API のバージョン依存が強いため、**実装着手時に最新ドキュメントで再確認する**こと。

---

## 4.1 権限

| 権限 | 必要な理由 | 対象 API | 対応方針 |
|---|---|---|---|
| `USE_EXACT_ALARM` | 分単位で正確に鳴らす | 33+ | アラームアプリは対象用途として認められる想定。インストール時付与 |
| `SCHEDULE_EXACT_ALARM` | 同上（下位バージョン用） | 31–32 | ユーザーに設定画面から許可してもらう導線が必要 |
| `POST_NOTIFICATIONS` | 鳴動通知・スヌーズ通知 | 33+ | 実行時パーミッション。初回起動時に要求 |
| `USE_FULL_SCREEN_INTENT` | ロック画面上に全画面アラームを出す | 34+ | アラーム用途は自動付与される想定。`canUseFullScreenIntent()` で実際の可否を必ず確認 |
| `RECEIVE_BOOT_COMPLETED` | 再起動後にアラームを再登録 | 全般 | 必須 |
| `FOREGROUND_SERVICE` + type 別権限 | 鳴動中のサービス継続 | 28+ / 34+ | → 4.3 |
| `VIBRATE` | バイブ | 全般 | 通常権限 |
| 電池最適化の除外 | OEM による強制停止の回避 | 23+ | 権限としてではなく**設定画面への誘導**で対応 |

**[要判断]** Google Play で `USE_EXACT_ALARM` / 完全なアラーム権限を使う場合、
公開時に用途の申告が必要になる可能性がある。個人利用（APK 直接インストール）なら不要。
→ 「Play 公開するか」の判断に依存（`06-open-questions.md` Q1）。

### 権限が無い状態のフォールバック
権限が欠けていても**アプリは動くが鳴らない**という最悪のパターンを避けるため:
- ホーム画面上部に恒久的な警告バナーを出す（FR-7.4）
- アラーム作成時に権限が無ければその場で要求する

## 4.2 確実に鳴らすためのスケジューリング

| 論点 | 方針 |
|---|---|
| API 選択 | **`AlarmManager.setAlarmClock()`** を使用 |
| 理由 | Doze / App Standby を貫通する唯一の確実な手段。副次的にステータスバーへ次のアラームが表示される |
| 使ってはいけない API | `WorkManager` 単体（実行時刻が最大数十分ずれる）、`setInexactRepeating()` |
| 登録数 | **常に 1 件のみ**（→ `03-domain-model.md` 3.4）。システムのアラーム数上限や電池消費を回避 |
| 再登録トリガ | 発火後 / 設定変更 / 再起動 / TZ 変更 / 日次セーフティネット |

### 端末再起動の扱い（★見落としやすい）

| 論点 | 内容 |
|---|---|
| 通常 | `BOOT_COMPLETED` は**ユーザーが画面ロックを解除した後**に届く |
| 問題 | 深夜に再起動 → 解除せず就寝 → 朝アラームが鳴らない |
| 対策案 | Direct Boot 対応（`LOCKED_BOOT_COMPLETED` + Device Protected Storage）で解除前にアラームを登録する |
| **判断（D-013）** | **対応しない。`BOOT_COMPLETED` のみとする。** レアケースに対して実装コストが見合わないため。DB を通常のアプリ内ストレージに置けるので、データ層が単純になる |
| 代替策 | 端末を再起動した際に「ロック解除するまでアラームは復元されません」と通知で案内する（要検討） |

## 4.3 鳴動中のプロセス維持（Foreground Service）

- 鳴動中は**フォアグラウンドサービス**で音・バイブ・タイマーを保持する（Activity だけだと落とされる）。
- Android 14 (API 34) 以降は**サービスタイプの宣言が必須**。
  - 候補 A: `mediaPlayback` … 実際に音を鳴らすので妥当。ただし用途審査で指摘される可能性
  - 候補 B: `specialUse` … 用途説明の記述が必要
  - **[要判断]** どちらを使うか。Play 公開しないなら実害は小さい
- Android 12+ の「バックグラウンドからの FGS 起動制限」は、
  **正確アラームの発火を受け取った直後は一時的に免除される**ため、この設計なら問題ない。

## 4.4 音・バイブ

| 論点 | 方針 |
|---|---|
| 音声ストリーム | `AudioAttributes.USAGE_ALARM` / `STREAM_ALARM` を使用 |
| マナーモード | USAGE_ALARM はマナーモードでも鳴る（アラームストリーム音量に従う） |
| おやすみモード (DND) | DND で「アラーム」が許可されていないと**鳴らない**。設定を検出して警告を出す |
| アラーム音量が 0 | 端末のアラーム音量が 0 だと無音。検出して警告を出す（★実際によくある事故） |
| オーディオフォーカス | 他アプリの再生を止めるためフォーカスを要求。逆に電話着信時は一時停止 |
| イヤホン接続時 | **対応しない（D-020）**。就寝時にイヤホンを使わないため。ただし鳴動先の切り替えを後から足せるよう、音声出力先の指定は 1 箇所に集約しておく |
| 音源ファイルの選択 | ユーザーが選んだ音楽ファイルの URI は権限が失効しうる。**アプリ内ストレージにコピーする**方式を推奨 |
| 音源が再生できない場合 | 端末既定のアラーム音にフォールバックし、無音になることを絶対に避ける |
| バイブ | `VibrationEffect` を使用。継続パターンを自前で定義 |

## 4.5 OEM 独自の省電力（★最大の実害ポイント）

Xiaomi / OPPO / vivo / Huawei / Samsung などは、標準の Doze とは別に
**独自の「アプリの自動起動禁止」「バックグラウンド強制終了」**を持つ。
これらが有効だとアラームが鳴らない。

**対応方針**
1. アプリ内に「アラームが鳴らないときは」ヘルプ画面を用意する
2. 初回オンボーディングで「電池の最適化から除外」を案内する
3. メーカーを検出し、可能なら該当設定画面へ直接遷移する Intent を用意する
4. 検証端末が限られるため、**「鳴らなかった」報告を受けられる導線**（設定内のトラブルシューティング）を置く

## 4.7 テスト戦略（アラームアプリ特有）

「実際に朝まで待って鳴るか確認する」は現実的でないため、以下を必須とする。

| レイヤ | 内容 |
|---|---|
| ユニットテスト（最重要） | `willRing(alarm, date)` の判定ロジック。祝日・除外日・予約日・グループ OFF の全組み合わせ |
| ユニットテスト | 「次の鳴動時刻」計算。年跨ぎ・うるう年・除外日連続・探索上限 |
| ユニットテスト | 一括作成の時刻生成（日跨ぎ 23:50 + 5 分 × 5 個 など） |
| 結合テスト | Room + Repository + Scheduler の再計算 |
| 手動テスト | 端末再起動 / 機内モード / DND / 電池最適化 ON の各状態での鳴動 |
| デバッグ機能 | 開発ビルド限定で「10 秒後に鳴らす」「任意日付で判定結果を見る」画面を用意する |
