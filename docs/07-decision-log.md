# 07. 決定ログ

確定した決定事項を時系列で記録する。
「なぜそう決めたか」を残すことで、後から蒸し返さずに済むようにする。

## 確定事項

| ID | 日付 | 決定事項 | 理由 |
|---|---|---|---|
| D-001 | 2026-09-03 | 対象プラットフォームは Android のみ | 要望どおり。iOS はスコープ外 |
| D-002 | 2026-09-03 | 差別化軸は「アラームの管理コストの削減」の 1 点に絞る | 音源の充実や睡眠計測など既存アプリとの機能競争はしない |
| D-003 | 2026-09-03 | コア価値は ①グループ一括 ON/OFF ②一括作成 ③予約日・除外日の事前登録 の 3 つ | 要望として明示されたもの |
| D-004 | 2026-09-03 | 音・バイブ・スヌーズ・祝日自動 OFF は「既存アプリ同等」を目標とし、独自性を求めない | 要望どおり |
| D-005 | 2026-09-03 | 睡眠トラッキング・天気読み上げ・SNS 連携はスコープ外 | 差別化軸から外れるため |
| D-006 | 2026-09-03 | クラウド同期は行わない。バックアップは JSON エクスポートで代替 | 個人利用前提、実装コスト過大 |
| D-007 | 2026-09-03 | **最初から Google Play 公開を前提に設計・実装する** | ユーザー判断（Q1）。権限の用途申告、プライバシーポリシー、ストア素材、targetSdk 追従、テスト要件を初期段階から織り込む → `09-play-release.md` |
| D-008 | 2026-09-03 | **「グループ内のいずれか 1 つを停止したら、その日の残りを自動スキップ」を実装し、グループ既定を ON にする** | ユーザー判断（Q2）。5 分おきアラームの最大の不満（起きた後も鳴り続ける）を解決する、本アプリ最大の差別化機能 |
| D-009 | 2026-09-03 | **無操作による自動停止では D-008 のスキップを発動させない** | 無操作で鳴り止んだ = まだ寝ている。明示的な停止操作のみを起床とみなす |
| D-010 | 2026-09-03 | **音・音量・バイブ・スヌーズ等の設定はグループが保持し、アラームは「継承」または「個別上書き」を選べる** | ユーザー判断（Q3）。一括作成した 10 個の設定を後から一括変更できないと、一括作成の価値が失われるため |
| D-011 | 2026-09-03 | **グループ ON/OFF と個別 ON/OFF は独立に保持し、AND で実効判定する（マスタースイッチ方式）** | 一括代入方式だと「5 個中 3 個だけ ON」という状態がグループ再 ON 時に失われるため。D-010 の前提でもある |
| D-012 | 2026-09-03 | **要件 → 設計（画面 / DB / アーキテクチャ）を文書で固めてから実装に入る** | ユーザー判断（Q15）。手戻りを減らす |
| D-013 | 2026-09-03 | **Direct Boot 対応は行わない**（`BOOT_COMPLETED` のみ） | ユーザー判断（Q12）。「深夜に再起動してロック解除せず就寝」というレアケースのみが対象で、実装コストに見合わない。DB をデバイス保護ストレージへ移す必要がなくなり、データ層が単純になる |
| D-014 | 2026-09-03 | **祝日データはアプリ内蔵とし、ユーザーが休日の追加・除去を手動でできるようにする** | ユーザー判断（Q7）。ネットワーク権限を持たずに済み、法改正のタイムラグや「祝日でも出勤」「お盆休み」を手動で埋められる |
| D-015 | 2026-09-03 | **除外日と予約日が重なった場合、どちらかを機械的に勝たせず、登録時に警告してユーザーに選ばせる** | ユーザー判断（Q6）。ただし警告 UI だけでは全ケースを拾えないため、未解決時の既定（除外優先）と反転設定も併せて用意する → FR-4.5 |
| D-016 | 2026-09-03 | **ウィジェット / 解除ミッション / エスカレーション / エクスポートは MVP に含めない** | ユーザー判断。まず MVP を最短で出し、Play 公開の工程に進む |
| D-017 | 2026-09-03 | **予約日（スポットアラーム）は MVP に含める** | コア価値 CV-3 が「予約日・除外日の事前登録」であり、予約日を外すと要望の一部が MVP から欠落するため |
| D-018 | 2026-09-03 | **深夜アラームは「その日の時刻」として扱い、0〜4 時台には UI で補足表示する** | ユーザー判断（Q20）。「前日の夜」モードを持つと除外日・祝日の基準日までずれてロジックが複雑になるため、内部は単純に保ち UI で誤解を防ぐ |
| D-019 | 2026-09-03 | **隔週 / シフト勤務などの高度な繰り返しは実装しない** | ユーザー判断（Q8）。曜日繰り返し + 除外日の一括登録で足りる |
| D-020 | 2026-09-03 | **「イヤホン接続時もスピーカーから鳴らす」オプションは実装しない** | ユーザー判断（Q10）。就寝時にイヤホンを使わないため |
| D-021 | 2026-09-03 | **要件フェーズを終了し、設計フェーズに移行する** | ユーザー判断。以降は画面設計 / データ設計 / アーキテクチャ / ロジック仕様を文書化する |
| D-022 | 2026-09-03 | **アプリ名は「タバネアラーム」、パッケージ名は `io.github.mmmio30.tabanealarm`** | ユーザーから命名を一任された。「束ねる」が本アプリの中核概念であり、「アラーム」を含むためストア検索にも乗る。既存の「グループアラーム」「アラームプラス」と区別できる造語。パッケージ名は独自ドメインが無いため GitHub アカウント名を用いる形式とし、公開後は変更できないため先に確定させた |
| D-023 | 2026-09-03 | **targetSdk 37（Android 17）で開発する** | Play は 2026-08-31 以降 API 36 以上を要求（期限は経過済み）。37 は 2027-08 に必須化見込みで、後から強制移行するより最初から適合させる方が安全。Pixel 8a で実機検証できる |
| D-024 | 2026-09-03 | **minSdk 26（Android 8.0）** | 対象端末を最大化する。クローズドテストで 12 人のテスターを確保する必要があるため、対応端末は広い方が有利。旧バージョンはエミュレータ検証となる点は許容する |
| D-025 | 2026-09-03 | **フォアグラウンドサービスの型は `mediaPlayback`** | Android 17 の公式ドキュメントが「`mediaPlayback` こそ while-in-use 能力を与える型」と明示している。実際には「正確アラーム権限 + `USAGE_ALARM`」の免除条件に依存するが、二重の保険になる（→ Q17 / A-2 解決） |
| D-026 | 2026-09-03 | **正確アラーム権限が無いときの「不正確なアラームによる代替登録」は実装しない** | Android 17 では権限が無いと発火時刻がずれるだけでなく、**音声再生自体が無言で失敗しうる**（4.4b）。「たぶん鳴る」状態を作るより、鳴らせないことを明確に警告する方が安全（→ A-4 解決） |
| D-027 | 2026-09-03 | **実機テストは Pixel 8a / Poco X7 Pro / Xperia 1 V の 3 台で行う** | ユーザーの保有端末。素の Android・Xiaomi の厳格な省電力・Sony 独自の省電力という、鳴らない原因の主要パターンを網羅できる |
| D-028 | 2026-09-03 | **Play Console のアカウント作成とテスター確保を、実装と並行して即座に着手する** | 個人用アカウントには公開前に 12 人 × 14 日間のクローズドテストが必須。MVP 完成後に着手すると、そこから最低 2〜3 週間は公開できない |

## 仮決定（合意が取れ次第、上の表へ昇格）

| ID | 仮決定 | 根拠 | 対応する質問 |
|---|---|---|---|
| T-001 | アラームは最大 1 つのグループに所属する（多対多にしない） | 多対多だと ON/OFF の意味が説明不能になる | — |
| T-004 | 除外日と予約日は同一テーブル（DateRule）で表現する | UI とロジックを共通化できる | — |
| T-005 | 除外日はアプリ全体 / グループ / アラームの 3 階層で持ち、OR で判定する | 「今週は全休」「平日グループだけ休み」を両方表現できる | — |
| T-007 | AlarmManager には常に「次の 1 件」だけを登録し、発火ごとに再計算する | 大量アラームでもシステム制限・電池消費を回避できる | — |
| T-008 | `setAlarmClock()` を使う | Doze を貫通する唯一の確実な手段 | — |
| T-010 | 「実効スケジュールのプレビュー」を MVP に含める | 設定要素が多く、鳴るかどうかをユーザーが推論できないため | — |
| T-012 | minSdk 26 / 単一モジュール構成 / Compose + Room + Hilt | 個人開発規模に対して妥当 | Q13 |
| T-013 | 一括作成は 1 回あたり最大 50 件まで | 際限なく作られると UI と再計算が破綻するため | — |
| T-014 | 一括作成したアラームは自動的に 1 グループにまとめる | グループ機能と一括作成は本質的にセットのため | — |
| T-015 | 音源選択は SAF（`ACTION_OPEN_DOCUMENT`）で行い、メディア読み取り権限を要求しない | 権限を減らすと Play 審査もプライバシー説明も単純になる（D-007 と整合） | — |
| T-016 | 選択した音源はアプリ内ストレージにコピーして保持する | URI 権限の失効・ファイル削除で無音になる事故を防ぐ | — |
| T-017 | 未解決の衝突は「鳴らさない（除外優先）」を既定とし、設定で反転できる | 警告 UI を通らない衝突（毎年繰り返し・インポート・上位階層の後付け）が必ず残るため | — |
| T-018 | 衝突の解決結果は既存ルールを書き換えず、独立した `DateOverride` として保存する | 期間ルールを分割すると意図とメモが壊れ、毎年繰り返しルールは分割できないため | — |
| T-019 | 内蔵祝日データは DB ではなくリソースとして持ち、ユーザー編集のみ DB に保存する | アプリ更新でデータを差し替えるときに DB マイグレーションが不要になる | — |
